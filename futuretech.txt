# Future Tech — Tuition Center Management Mobile Application

Build a production-ready mobile application called **Future Tech** for managing a tuition/learning center with a large number of students from different colleges, schools, departments, and academic years.

The application must be clean, modern, responsive, secure, and easy for a single Admin to manage.

---

**Future Tech**

Use **Future Tech** consistently in:

* App name
* Splash screen
* Login screen
* Registration screen
* Dashboard
* App bar/header
* Email templates
* Notifications
* App metadata

Suggested branding:


There are exactly **two user types**:

# 3. Important Meaning of "Batch"

In Future Tech, **Batch does NOT mean a tuition class or a group attending at a particular time.**

Batch means the student's **academic batch**, determined by:

```text
Joining Year → Passing Year
```

Examples:

### Engineering

```text
Joining Year: 2023
Passing Year: 2027

Academic Batch:
2023–2027
```

Engineering normally has 4 years.

### Arts / Science

```text
Joining Year: 2023
Passing Year: 2026

Academic Batch:
2023–2026
```

Arts/Science normally has 3 years.

The system should calculate/display:

```text
academic_batch = joining_year + "–" + passing_year
```

Do not create a separate `batches` table for tuition classes.

# 23. Academic Batch

Do not create a separate `batches` table.

Academic batch is derived from:

```text
joining_year
+
passing_year
```

Example:

```text
joining_year = 2023
passing_year = 2027

academic_batch = "2023–2027"
```

Store it only if useful for efficient display/search, or calculate it dynamically.

The backend must validate that:

```text
passing_year > joining_year
```

# 24. Fees

Admin can assign fees to individual students.

There is no tuition-batch fee system.

Database:

```text
fee_records
--------------------------------
id                  BIGINT PK
student_id          BIGINT FK → students.id
fee_name            VARCHAR
total_amount        DECIMAL(10,2)
discount_amount     DECIMAL(10,2)
final_amount        DECIMAL(10,2)
due_date             DATE
status              ENUM(
                        'PENDING',
                        'PARTIALLY_PAID',
                        'PAID',
                        'OVERDUE',
                        'CANCELLED'
                      )
created_at          TIMESTAMP
updated_at          TIMESTAMP
```

Calculation:

```text
final_amount =
total_amount - discount_amount
```

---

# 25. Payments

```text
payments
--------------------------------
id                  BIGINT PK
fee_record_id       BIGINT FK → fee_records.id
student_id          BIGINT FK → students.id
amount              DECIMAL(10,2)
payment_date        DATE
payment_method      ENUM(
                        'CASH',
                        'UPI',
                        'BANK_TRANSFER',
                        'CARD'
                      )
transaction_id      VARCHAR NULL
receipt_number      VARCHAR UNIQUE
remarks             TEXT NULL
created_at          TIMESTAMP
```

Pending amount:

```text
pending =
final_amount - SUM(payments.amount)
```

Do not manually maintain a separate pending amount that can become inconsistent.

# 50. Business Rules

Implement these rules strictly:

1. Only one Admin account is supported.
2. Students must register before accessing the application.
3. New students must wait for Admin approval.
4. Students cannot login to the full application before approval.
5. Students must complete their profile after approval.
6. Students cannot modify fees.
7. Students cannot modify payments.

# 53. Most Important Requirement

Do not misunderstand the concept of **Batch**.

For Future Tech:

```text
Batch ≠ Tuition Class
Batch ≠ Time Slot
Batch ≠ Staff Group
```

Instead:

```text
Academic Batch = Joining Year – Passing Year
```

Examples:

```text
Engineering
2023–2027

Arts & Science
2023–2026
```

Use this academic batch for:

* Student filtering
* Student search
* Reports
* Task targeting
* Student profile
* Academic information

Do not create a tuition-class `batches` table.
